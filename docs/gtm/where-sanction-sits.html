01Slack-approved deploy/spendShipped

WhoStaff engineer running Claude Code; eng lead approving in #eng-approvals (Slack OAuth install) Wherestdio sanction-mcp (or SDK middleware) + the Slack interactive app for the human moment
  1. Mid-task, the agent wants a $180 Datadog seat → POST /v1/authorize with its pxy_ key.
  2. $180 sits in the escalation band → escalated + request_id; a PendingApproval persists.
  3. Sanction posts the Approve/Deny card to the channel. The eng lead reads it and taps Approve — the click is HMAC-verified and recorded as slack:<username>.
  4. Approval mints a single-use, TTL'd grant; the agent retries with grant_id → approved, grant consumed atomically.
  5. Nobody clicks in time → the policy's timeout action settles it. Nothing hangs.

Replaces: a card number in env with no ceiling, or a human copy-pasting approval into nothing auditable. Here the approval is a recorded actor, a one-use grant, and a replayable evidence trail.

02The governed MCP toolchainShipped

WhoPlatform team fronting GitHub + internal MCP servers; ops registers upstreams with the sk_ key; agents hold only pxy_ WhereMCP broker — hosts point at /mcp/broker/github instead of the upstream
  1. Ops registers the upstream once: URL + auth header, vaulted as mcp:github — the GitHub token never enters any agent's config.
  2. Tool rules: delete_repo and payments.charge block; merge_pr escalates; reads allow. Rules inherit down the wallet tree.
  3. Every tools/call is authorized before forwarding; batched calls containing tools/call are refused outright.
  4. A prompt-injected delete_repo comes back as an MCP isError result — the upstream never sees it.
  5. Approved forwards get fresh outbound headers: vaulted token injected server-side, the agent's Sanction key never leaks upstream, the grant _meta stripped.

Replaces: the PAT in every developer's MCP config and "don't delete repos" as a system-prompt plea. On brokered traffic the deny is structural — a hijacked agent cannot invoke what policy forbids, and can't exfiltrate a token it never held.

03x402 paid APIs — the stablecoin workflowLedger shippedGate next

WhoResearch agent (LangGraph / Vercel AI SDK) consuming paid APIs that quote 402 in USDC on Base; owner sets caps; CFO reads the CSV WhereToday: SDK/REST authorize-before-sign with settlement metadata (STABLE-0). Next: the x402 spend gate intercepting the handshake (STABLE-1)
  1. Vendor replies 402 + x402 requirement: $0.04 USDC on Base.
  2. Agent calls POST /v1/authorize with settlement: {rail: "x402", asset: "usdc", network: "base"} — closed vocabulary; off-vocabulary rails 400.
  3. Approved → the wallet signs and the request resends with payment. Denied → the transfer is never signed. Irreversible rail: the pre-transaction decision is the only control point.
  4. Settlement persists on the decision row — the CFO's audit CSV carries a settlement column next to amount, merchant, decision.
  5. Next (STABLE-1): the gateway/broker sees the 402 quote itself and runs the authorization before the signing step can proceed. Veto-only: Sanction can say no, never go.

Replaces: a funded hot wallet whose only budget is its balance. The same ladder, escalation band, and audit trail now stand in front of chain spend as card spend.

04LLM spend chargeback across an orgShipped · flagship

WhoVP Eng owns the Engineering wallet with Platform / ML / Support children; each team's agents are seats; FinOps pulls the CSV WhereLLM gateway — model SDK base URL → /api/gateway/anthropic + x-sanction-key. Zero per-call instrumentation
  1. Build the tree, set subtreeDailyCapUsd on the root — enforced atomically, so sibling teams can't race past the parent cap.
  2. Each runtime changes one line: the base URL and a header.
  3. The gateway reads usage off every response and meters it. Over budget → 402 before the call reaches the provider.
  4. Console: month runway, projected exhaust dates, seat health, wallet → seat.
  5. Mid-month overspend → reallocate budget between teams (audited) or freeze a runaway subtree.
  6. FinOps: reporting summary + audit CSV → chargeback journal entries per team.

Replaces: one shared org API key, a surprise invoice, and a spreadsheet guessing which team burned it. Enforcement, not dashboarding — and chargeback comes from the same ledger that enforced. This is the confirmed primary use case.

05AP automation with dual controlShipped

WhoInvoice-payment agent in LangGraph; the controller approves in Slack; the external auditor replays evidence quarterly WhereRaw REST per payment. Veto-only and non-custodial: the ERP/bank rail executes, only ever on an approved decision
  1. Policy: auto-approve ≤ $500, escalate to $10,000, hard-deny above; optional off-hours conditional rule.
  2. Per invoice: /v1/authorize with idempotency key = invoice number — a retried run replays the original decision instead of double-paying.
  3. A $7,800 invoice escalates → the controller approves in Slack; the grant is single-use with a TTL — no standing authority accumulates.
  4. Retry with grant_id → approved → the ERP executes.
  5. Audit season: evidence replay reproduces each decision from its stored context; the hash-chained export verifies self-contained — no database access needed.

Replaces: "the bot only pays what's in the approved-vendors sheet" plus monthly reconciliation. Real dual control per payment, segregation of duties recorded, tamper-evident proof — with Sanction never touching money-transmitter surface.

06Governed credentials for ephemeral jobsShipped

WhoNightly batch agent on a cron runner needing a DB password and a Stripe restricted key for ten minutes Where/v1/exec + /v1/credentials/inject — 15-minute mandate JWTs over the envelope-encrypted, RLS-isolated vault
  1. Owner vaults secrets once with labels and a minClearance each; the seat carries a clearance level.
  2. The job's only baked-in secret is its pxy_ key. It requests a scoped execution: labels + TTL + budget.
  3. Clearance checked per label — any miss is a 403 naming the denied labels. A scoped JWT comes back.
  4. Each injection decrypts server-side, returns the secret to memory only, and writes an immutable audit row.
  5. The JWT dies at 15 minutes; a compromised runner is one revoke call from dead now.

Replaces: long-lived secrets in CI env vars — unrotated, unattributed, invisible when leaked. Real credentials exist outside the vault for fifteen minutes, gated by clearance, every access logged.

07Policy-as-PDP for an existing platformShipped

WhoA SaaS company embedding agents in its product. Their middleware enforces; their customers' admins tune limits; identity stays in their stack WhereAuthZEN PDP — POST /api/access/v1/evaluation per governed action; wallet-per-tenant in their tree
  1. Tenant onboarding: child wallet + a seat template stamped across the tenant's agents.
  2. Observe first: the real engine records would-be denials (with dollars attached) while blocking nothing — a week of zero-risk evidence.
  3. Then enforce: one flip. The middleware pre-flights every action; evaluations are decision-only, so aggressive pre-flighting is free.
  4. Denies carry stable machine codes + remediation, so their agent replans instead of guessing. Subject spoofing fails closed.
  5. Escalations ride the AARP loop: signed binding token → real Sanction escalation → re-evaluate with the approval id, grant consumed once.

Replaces: per-tenant limit columns checked inconsistently across services, no approval loop, no evidence. A standards endpoint means zero vendor-specific code in their enforcement layer, and observe→enforce means adoption never starts with a customer-visible outage.
